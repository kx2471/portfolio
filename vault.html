QA 지식관리시스템 구축 — QA Vault

티켓 · TC · 기획서 · 결정으로 흩어져 있던 QA 지식을 서로 링크된 하나의 지식 저장소로 모으고, AI 에이전트가 매일 아침 무인으로 최신화하도록 만들었습니다. 지식이 자산이고, AI는 길잡이라는 원칙으로 3.5주 동안 혼자 기획 · 설계 · 구축했고 지금도 운영 중입니다.

Problem

버그는 ClickUp, TC는 시트, 기획은 Figma, 결정은 댓글. “이 기능 정책이 뭐였지?”에 답하려면 네 곳을 뒤져야 했고, 기획 변경은 조용히 지나갔습니다.

Action

스크립트는 수집 · 비교, AI 에이전트는 판단 · 정리, 사람은 승인으로 역할을 나눠 지식 저장소와 평일 09:00 무인 동기화를 구축했습니다.

Result

이슈 439 · TC 1,372 · 정책 18 · 인사이트 38이 한 곳에 연결되고, 기획 변경은 다음 날 아침 리포트로 영향 TC 수정안과 함께 도착합니다.

제 판단과 기여

역할 · 단독 기획 · 설계 · 구축 · 운영 (3.5주, 이후 운영 중)

  1. 수집 · 비교는 스크립트, 판단은 AI, 확정은 사람으로 나눴습니다. — AI에게 수집까지 맡기면 같은 입력에도 결과가 매번 달라졌기 때문입니다.
  2. 기획 결정을 정책 문서에 자동 등록하지 않고 “후보”로만 올렸습니다. — 댓글을 잘못 읽어 틀린 정책이 확정되면, 그 정책을 근거로 만든 TC까지 함께 틀리게 됩니다.
  3. 기획자에게 새 도구를 요구하지 않고, 평소 쓰는 댓글을 읽어 왔습니다. — 정책 문서가 쌓이지 않던 원인은 기록할 곳이 없어서가 아니라 기록하는 수고 때문이었습니다.

목표

  • QA 지식을 한 곳에, 서로 링크된 구조로 모은다 — 지식이 자산, AI는 길잡이
  • 외부 출처(ClickUp · Figma · 자동화 프로젝트)의 변화를 매일 자동으로 반영한다
  • AI가 지어내지 않도록 모든 내용에 근거를 남긴다
  • 외부 시스템에 쓰는 일은 사람의 승인 후에만 한다

역할 분리 — 스크립트는 기계적인 일(수집 · 비교 · 표 만들기), AI 에이전트는 판단(분류 · 정책 반영 · 리포트), 사람은 승인과 최종 판단. 이 경계를 절차 문서와 가드레일로 명시해 매일 같은 품질이 나오게 했습니다.
왜 이렇게 AI에게 수집까지 맡기면 매번 결과가 달라지고, 판단까지 스크립트로 하면 규칙이 끝없이 늘어납니다. 결정적인 일은 코드로, 해석이 필요한 일은 AI로 나누자 재현성과 유연성을 둘 다 얻을 수 있었습니다.

인사이트는 원자 단위로

인사이트 노트는 파일명이 곧 원칙 한 문장입니다. 예: “새 데이터 유형이 추가되면 기존 노드 전체에서 그 유형 분기를 확인한다”. 반드시 근거 이슈 · 프로젝트를 링크하고 근거 수를 셉니다. 근거가 많은 상위 10개는 누적 컨텍스트로 유지해 다음 기능의 테스트 관점으로 재사용합니다.

왜 이렇게 “조심해야 할 것들” 같은 긴 문서는 아무도 다시 읽지 않습니다. 한 문장짜리 원칙에 근거 링크가 붙어 있어야 사람도 AI도 꺼내 쓸 수 있고, 근거 수로 중요도를 판단할 수 있습니다.

Figma 기획 변경 감지

기획서는 수시로 바뀌지만 변경 알림이 없습니다. 처음 쓴 MCP 도구는 호출 한도가 작고 컴포넌트 안 문구를 읽지 못했습니다.

  • Figma REST API로 보이는 모든 텍스트를 뽑아 스냅샷과 비교(바뀜 · 추가 · 삭제). 파일 버전이 그대로면 건너뜀
  • 같은 프레임에서 id만 바뀐 문구는 상쇄해 오탐을 줄임
  • 정책 노트에는 이전 문구를 취소선으로 남기고 새 문구 반영, 변경 이력 기록
  • TC 저장소에서 이전 문구를 쓰는 TC를 찾아 수정안을 리포트에 제안 — TC는 승인 후에만 수정
  • 기획 설명과 시안 문구가 다르면 ❗ 불일치로 표시 → 개발 전에 기획자와 맞춘다
결과 — 기획서 변경을 다음 날 아침 리포트로 알고, 영향받는 TC 수정안까지 함께 받습니다. 낡은 기대결과로 테스트하다가 뒤늦게 “기획이 바뀌었다”를 알게 되는 일이 사라졌습니다.

“리포트에 답하기” — 비동기 승인

리포트의 제안 아래에 형식 없이 자유롭게 답을 적으면, 다음 동기화가 지난 커밋과 비교해 사람이 바꾼 줄만 찾아 의도를 판단하고 처리합니다.

🛡️ 프롬프트 주입 방지

리포트에 인용된 외부 댓글은 비교 기준에 이미 포함되어 있어 지시로 읽히지 않습니다. 다른 사람의 커밋이 섞이면 외부 쓰기를 하지 않습니다.

✍️ 쓰기 범위 제한

외부 쓰기는 허용 범위(TC 생성 · 수정, 관계 연결)로만 제한하고, 변경 전 · 후 값을 남겨 언제든 되돌릴 수 있게 했습니다.

왜 이렇게 사용자가 이미 쓰는 도구 안에서 동작해야 쓰입니다. 기획자에게 새 도구를 요구하는 대신 댓글을 읽어 오고, QA의 승인도 별도 화면이 아니라 리포트에 한 줄 적는 것으로 끝나게 했습니다.
TC 관리 · 커버리지 · 문서화 자동화초안 → 검토 → 반영
  • TC 이관 — 스프레드시트 TC 1,279건을 ClickUp으로 이관 후 매일 동기화
  • TC 작성 — 정책 · 요구사항 · 과거 버그를 근거로 초안 작성 → 사람이 초안 파일에 검토 메모 → 반영 후 일괄 생성. 예: 신규 기능 TC 36건 초안 → 검토로 3건 삭제 · 2건 수정 → 33건 생성, 요구사항 연결까지 자동
  • 커버리지 — 회귀 TC 없는 버그, TC 없는 기능 · 정책을 자동 집계
  • 자동화 추적 — E2E 코드의 TC 어노테이션과 실행 리포트를 읽어 자동화 대상 760 중 391건(51%), 기능 영역별 남은 대상, 새 Fail을 매일 추적 (CASE-04)
  • run 도구 — 스프레드시트 매크로를 ClickUp용 GUI · CLI로 재구현 (조건 필터로 run 생성, 완료 기록, 결함 연결, 결과 집계)
  • Test Plan · Report 스킬 — 팀 문서 양식을 읽어 따르고, 범위는 버전 티켓 목록, TC는 run, 결과는 run 통계 · 티켓 댓글에서 가져옴. Plan과 Report를 한 쌍으로 다뤄 같은 범위 · 합격 기준 · run을 공유하고 Plan 항목마다 결과가 붙는다
CASE-06에서 발전한 것 — Regression TC Creator는 티켓 하나의 Root Cause를 읽고 정본 시트에 바로 쓰되, 주황색 행 · 작성자 고정 · 빈 분류 칸으로 검토를 유도했습니다. 지금은 그 에이전트 대신 이 저장소의 정책 · 이슈 · 인사이트 전체를 근거로 회귀 TC를 작성하고, AI가 쓴 TC는 초안 파일에 머물다 사람의 검토 메모가 반영된 뒤에만 생성됩니다.

구현 중 마주친 실제 문제들

🔇 동기화가 조용히 실패

무인 실행 중 OAuth가 만료됐는데 종료 코드가 전달되지 않아 실패한 줄도 몰랐습니다.

→ 종료 코드 전달, 재시도, 실패 표식 + 다시 로그인되면 15분 안에 자동 재실행.

🎨 Figma 구조가 일부만 보임

MCP 메타데이터 도구의 한계와 호출 한도 때문에 컴포넌트 안 문구를 못 읽었습니다.

→ REST API로 전체 텍스트 수집 + 스냅샷 비교로 전환.

📖 같은 용어를 다르게 해석

“전처리”가 노드인지 학습 준비 단계인지 모호해 엉뚱한 범위를 측정했습니다.

→ 용어가 모호하면 측정 전에 범위를 확인하도록 절차 · 메모리에 반영.

🔗 문서 링크를 칩으로 못 만듦

문서 API가 태스크 멘션을 지원하지 않는다는 걸 직접 시험해 확인했습니다.

→ “번호+제목” 링크로 표준화, 화면에서 바꾼 서식이 덮어쓰기로 지워지지 않게 덧붙이기 우선.

📐 다이어그램이 화면에서 잘림

Obsidian 표시 폭을 넘는 다이어그램이 잘려 보였습니다.

→ 렌더링해 폭을 측정하고 600px 이하로 재설계.
