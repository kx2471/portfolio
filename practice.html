검증 실무 — 산출물 · API 검증 · 업무 도구

SWR · TC · Defect · Xray 추적성 같은 QA 표준 산출물과, UI 뒤를 직접 두드리는 API 검증, 반복 업무를 줄이려고 만든 유틸리티들입니다.

Problem

요구사항–TC–결함이 따로 놀았고, UI에서 막히는 값이 서버에서도 막히는지는 확인되지 않았습니다.

Action

추적성 체계를 세우고, API 레벨로 내려가 검증하고, 반복은 도구로 줄였습니다.

Result

요구사항 커버리지와 결함 추적성 확보, 서버 측 검증 부재 발견·개선 주도.

QA 산출물 — 요구사항에서 결함까지 추적 가능하게SWR · TC · Defect · Xray

Test Case 설계 기법

기법 정의보다 실제로 무엇을 만들어 관리했는지를 남깁니다.

기법적용한 방식남긴 것
요구사항 기반 요구사항 문서를 항목 단위로 쪼개 빠진 기능이 없는지 대조 Jira 등록 후 요구사항 ID와 매핑
동등 클래스 분할 입력값 범위·조건을 분석해 유효/무효 클래스로 나누고 대표값 선정 필드별 클래스 정의 — 최소 TC로 최대 결함
경곗값 분석 각 필드의 최솟값·최댓값과 직전/직후를 도출. off-by-one 방지 min · min-1 · max · max+1
오류 추정 과거 결함 이력 · 복잡한 로직 · 사용자 오용 시나리오로 의심 영역을 좁힘 정형 기법으로 안 잡히는 엣지 케이스
기법을 나눠 관리한 이유 — 어떤 기법으로 만든 TC인지가 남아 있어야 커버리지의 성격을 말할 수 있습니다. “TC 300개”보다 “요구사항 전 항목 대조 + 경계값 조합 + 과거 결함 기반 의심 영역”이 훨씬 정확한 진술이고, 회귀 대상을 고를 때도 이 축이 기준이 됩니다.

Xray 기반 추적성

요구사항과 TC의 연결로 추적성을 확보하고, 결함 관리 연동으로 양방향 추적이 가능합니다.

  • Requirement Traceability — 모든 요구사항이 TC로 연결되어 충족 여부 판단 가능
  • Defect Traceability — 결함에서 역방향으로 실행 이력 · TC · 요구사항까지 추적
  • Test Set(기능별 TC 관리) · Test Plan(스케줄) · Test Execution(실행 결과)로 라이프사이클 통합 관리
API 검증 — UI 뒤를 직접 두드린다서버 측 검증 부재 발견

프론트엔드 유효성 검증은 사용자에게 친절한 장치일 뿐 품질 보증이 아닙니다. 그래서 UI를 거치지 않고 REST API를 직접 호출해 같은 규칙이 서버에서도 지켜지는지 확인했습니다.

왜 이렇게 UI 자동화는 “막히는 것”만 확인합니다. 화면에서 막혔다는 사실은 서버가 막았다는 증거가 아니라 화면이 요청을 보내지 않았다는 증거일 뿐입니다.

화면을 거치지 않기 때문에 가능한 것

  • 타입·정밀도 경계를 그대로 통과시켜 본다 — 정수 필드에 실수를, 불리언에 문자열을 넣었을 때 서버가 무엇을 저장하는지
  • 도달하기 어려운 상태를 만들어 놓고 시작한다 — 배포 상태 같은 값을 직접 PUT으로 세팅하면 UI로 몇 단계 거쳐야 하는 전제 조건을 한 번에 구성
  • 거부돼야 할 요청을 만들어 보낸다 — 인증 헤더를 빼거나 바꿔서, 통과하는 경우가 아니라 막혀야 하는 경우를 확인

발견 사례 — 프론트만 막고 있던 유효성 검증

진행

  • DevTools로 회원가입·회원정보 수정 요청 패킷 추출
  • 파라미터 구조와 인증 방식 분석
  • Postman·cURL로 형식 위반 값과 <script> 태그를 삽입해 전송
  • 응답만 보지 않고 DB 저장 여부와 관리자 페이지 반영까지 추적

발견

  • 서버 측 입력값 검증 부재 — 프론트엔드 검증만 존재
  • 형식·규칙을 위반한 데이터가 그대로 DB에 저장
  • 주입한 스크립트가 관리자 페이지에서 렌더링되는 경로 확인 → XSS

보고

  • 재현 절차를 그대로 옮길 수 있게 정리
  • 스크린샷과 패킷 로그를 증거로 확보
  • UI 결함이 아니라 서버 검증 로직 부재로 원인 규정
  • 개선 방향까지 제안해 수정 주도
화면 기준 테스트만 했다면 끝까지 발견되지 않았을 결함입니다. 그 뒤로 폼이 있는 기능은 UI 통과와 API 통과를 별도의 검증 항목으로 나눠 씁니다.
