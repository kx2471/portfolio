AI 시대의 품질,
검증할 수 있게 만듭니다.

김상옥 · Kim Sang-Ok

사람이 무엇을 봐야 하는지 정하고, 빠르고 제대로 볼 수 있게 만드는 QA입니다. 지금은 산업 AI 비전 검수 플랫폼 Daisy의 품질을 책임지며, AI 제품의 출력을 판정할 기준을 세우고, 검증 프로세스 · 자동화 · 도구를 0에서 설계하고 있습니다.

제 강점은 판정 기준이 없는 곳에 기준을 세우고, 그 기준이 사람의 주의가 아니라 구조로 지켜지게 만드는 것입니다. 규칙은 트래커 자동화에, 판정은 데이터에, 검증은 누구나 돌릴 수 있는 도구에 걸어 둡니다.

VIEW

이 일에서 중요하다고 보는 것

QA의 일은 버그를 찾는 데서 끝나지 않는다고 생각합니다. “이 상태로 내보내도 되는가”에 팀이 근거를 갖고 같은 답을 낼 수 있게 만드는 것이 이 직무의 핵심입니다. 아래 여섯 가지를 일하는 기준으로 삼고 있고, 각 기준은 실제 작업으로 확인할 수 있습니다.

✓
① 판정 기준 — 누가 봐도 같은 결론이 나야 한다
“이거 Urgent인가요?”, “RC 끝난 건가요?”가 매번 논쟁이면 품질은 목소리 큰 사람이 정합니다. Priority는 4단계 판단 흐름으로, RC 종료는 잔여 Urgent 0 · Pass Rate 95% 같은 숫자로 정했습니다. 정답이 하나가 아닌 LLM 출력은 개별 응답이 아니라 데이터셋 단위 정확도로 판정했습니다.
CASE-03 · CAREER
✓
② 근거 — 통과한 것도 “무엇을 봤는지” 남아야 한다
PASS 숫자는 그 자체로 검증 대상입니다. 통과한 테스트가 범인이었던 경험 뒤로, 리포트에는 검증 포인트와 그 시점 화면을 남기고 재시도 후 통과는 “불안정”으로 따로 분류합니다. AI가 답할 때도 원본 링크를 붙이고, 자료에 없으면 “모른다”고 하게 합니다.
CASE-01·02·04·05
✓
③ 구조 — 사람의 주의에 기대는 규칙은 바쁠 때 깨진다
Root Cause를 안 쓰고 넘기면 트래커가 자동으로 되돌립니다. 사고가 나면 사람을 찾기보다 같은 일이 구조적으로 불가능해지는 지점을 찾습니다. AI가 쓴 결과도 표시만 하지 않고, 사람이 승인해야 정본이 되는 관문을 둡니다.
CASE-01·03·06
✓
④ 자동화의 목표는 QA가 돌리는 게 아니라, 누구나 검증할 수 있는 환경이다
QA가 모든 변경의 관문이 되면 QA가 병목이 됩니다. 그래서 평소에는 검증 환경을 제공하고 — 브라우저로 돌리는 러너, Slack에서 묻는 정책 Agent — 막아야 할 곳은 배포 직전 한 지점으로 모읍니다. 그 지점에서는 빌드 번호 기준 게이트와 NO-GO 차단권으로 확실히 막습니다. 환경은 갖췄고, 팀 전체가 실제로 쓰게 만드는 것이 지금의 과제입니다.
CASE-02·03·05
✓
⑤ 새 테스트를 늘리는 것보다, 기존 자산을 쓰는 방식을 바꾼다

CASE-02·05·06
개발자 · 기획자와 일하는 방식 — 의견을 내는 건 QA의 몫이고, 반영 여부는 상대가 정합니다. 기획과 시안이 다르면 ❗ 불일치로 표시해 기획자와 맞추고, 댓글 속 결정은 정책 “후보”로만 올리고, 서버 검증 부재는 개선 방향까지 제안하되 결정은 담당자에게 둡니다. 예외는 미리 합의한 한 지점, 배포 게이트뿐입니다. 그곳에서도 QA는 품질 사실로 NO-GO를 걸고, 최종 GO는 PM이 정합니다.

AI 시대에 이 기준이 더 중요해지는 이유

AI가 결과물을 싸고 빠르게 만들수록 병목은 “그걸 믿어도 되는가”로 옮겨갑니다. 사람이 전부 들여다보면 사람이 새 병목이 되고, 결국 검수는 도장 찍기가 됩니다. 그래서 저는 같은 기준을 두 방향에 씁니다.

🧪 AI 제품을 검증한다

정답이 하나로 정해지지 않는 출력을 판정할 기준을 세웁니다. LLM 매칭의 데이터셋 정확도(%) 판정, 비전 검출의 가능 여부 근거, 이상 탐지 지표의 집계 기준이 그것입니다. (경력)

🤖 AI로 검증한다

AI와 자동화가 일을 맡되, 그 결과를 사람이 검증할 수 있는 형태로 남깁니다. 근거 링크가 붙은 답, 초안 → 검토 → 승인 관문, 판정 근거를 남기는 리포트가 그것입니다. (CASE-01 · CASE-02 · CASE-04 · CASE-06)

다음 목표 — 검수가 반드시 일어나는 루프

① 검수 관문 일부 구현

AI 결과가 바로 정본이 되지 않고, 사람이 승인해야 정본이 되는 구조. TC 작성에는 CASE-01에서 적용했고, 위험도에 따른 차등 검수로 넓히려 합니다.

② 근거가 붙은 결과

결과마다 어느 근거에서 나왔는지가 붙어, 직접 만드는 것보다 검수가 빠르도록.

③ 반려 사유 반영

반려 사유를 분류해 기록하고 규칙에 반영해, 다음에는 사람이 볼 양 자체가 줄어들도록.

④ 측정

승인율 · 수정 후 승인율 · 검수 시간 대비 직접 작성 시간, 그리고 누가 승인했는지까지 기록.

LESSONS

실패에서 고친 것

기준은 성공보다 실패에서 더 많이 바뀌었습니다. 실패를 운이나 개인 실수로 넘기지 않고, 원인을 증거로 확정한 뒤 같은 실패가 구조적으로 반복되지 않게 만드는 데까지 가는 것을 원칙으로 합니다.

🟥 통과한 테스트가 범인이었다

무엇이 틀렸나 — 학습 완료를 화면 토스트로 판정했더니, 부하가 걸린 날 6분짜리 학습이 26초 만에 “통과”했습니다.

어떻게 확정했나 — 리포트 타임라인을 재구성하고 DOM 스냅샷을 시점별로 대조했습니다.

무엇을 바꿨나 — 판정 근거를 노드 상태 · 다운로드 파일 · 요청 페이로드로 옮기고, 리포트에 통과한 항목도 검증 포인트와 화면을 남기게 했습니다. (CASE-04 · CASE-05)

🟧 원인을 모른 채 만든 우회 구조

무엇이 틀렸나 — 병렬 실행 시 세션이 끊기는 문제를 피하려고 탭 orchestration 구조를 만들었는데, 그 자체가 단일 실패점이 됐습니다.

어떻게 확정했나 — “계정당 단일 세션”이라는 그럴듯한 가설과 “수동은 된다”는 사실이 모순이라 실험을 이어갔고, 세션이 기기(User-Agent) 단위임을 밝혔습니다.

무엇을 바꿨나 — worker별 UA를 분리해 병렬 1 → 3 worker를 복구하고, 이미 만든 우회 구조는 폐기했습니다. (CASE-04)

⬛ 조용히 실패한 무인 동기화

무엇이 틀렸나 — 무인 실행 중 로그인이 만료됐는데 종료 코드가 전달되지 않아, 동기화가 실패한 줄도 몰랐습니다.

무엇을 바꿨나 — 종료 코드 전달, 재시도, 실패 표식을 남기고, 다시 로그인되면 15분 안에 자동 재실행되게 했습니다. 자동화는 실패가 보여야 완성입니다. (CASE-01)

⬜ 같은 단어, 다른 범위

무엇이 틀렸나 — “전처리”가 노드 하나인지 학습 준비 단계 전체인지 확인하지 않고 측정해, 서로 다른 범위를 놓고 숫자를 맞춰 보는 일이 생겼습니다.

무엇을 바꿨나 — 용어가 모호하면 측정 전에 범위부터 확인하도록 절차와 에이전트 규칙에 넣었습니다. 숫자가 정확해도 범위가 틀리면 틀린 보고입니다. (CASE-01)
