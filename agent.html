AI Agent — Regression TC Creator

제가 의무화한 Root Cause 기록을 읽어 회귀 TC를 설계하고, Google Sheets에 기록하고, 티켓에 코멘트와 필드까지 연결하는 Claude 기반 Agent입니다. 정책을 만든 사람이 그 정책이 남긴 데이터를 쓰는 도구를 직접 만들었습니다.

Problem

RCA 기록은 쌓이는데 활용이 안 되는 자산이 될 위험이 있었고, 회귀 TC 설계·기록·연결은 매 스프린트 반복되는 수작업이었습니다.

Action

MCP 도구 조합 · 3단계 게이팅 · 안전장치를 포함한 시스템으로 구현했습니다.

Result

티켓 ID 한 줄이면 TC 설계·시트 기록·티켓 연결이 자동으로 끝납니다. 타 팀이 사내 업무 개선 사례로 공유했습니다.

왜 만들었는가 · 동작 흐름정책이 남긴 데이터를 쓰는 도구

QA 워크플로우를 설계하면서 버그 티켓의 Root Cause · Corrective Action을 기록하도록 의무화했습니다. 그런데 이 정보는 기록만 되고 활용이 안 되는 자산이 될 위험이 있었습니다 — 매 스프린트마다 버그 티켓을 일일이 읽고, 회귀 TC를 손으로 설계하고, 시트에 기록하고, 원본 티켓에 연결하는 과정이 단순 반복의 연속이었습니다.

세 가지 쓰기 작업은 앞 단계가 성공해야 다음이 진행됩니다. 일부만 게시되는 불완전 상태를 원천적으로 차단하기 위함입니다.

호출은 한 줄이면 끝난다

에이전트를 서브에이전트로 등록해 두고, 티켓 ID 하나만 자연어로 넘기면 됩니다. 별도 설정이나 옵션 플래그 없이 기본 시트에 기록되도록 기본값을 잡아, 쓰는 사람이 매번 결정할 것을 없앴습니다.

왜 이렇게 도구의 채택률은 기능 수가 아니라 처음 쓸 때의 마찰에서 갈립니다. “무엇을 설정해야 하지?”가 한 번이라도 떠오르면 사람들은 그냥 손으로 합니다.
설계 원칙 — QA 엔지니어의 사고 과정을 명문화RCA 기반 · 5축 스캔 · 양보다 질

1. RCA 기반 TC 설계

단순히 티켓을 요약하는 게 아니라, 과거 실패 모드를 재현하는 일을 합니다.

  • Root Cause가 명시된 경우 → 그 실패 모드를 재현하는 명시적 케이스 설계
  • Corrective Action이 실제로 막거나 처리하는지 확인하는 회귀 케이스 추가
  • 같은 근본 원인의 영향을 받을 수 있는 인접 경계 조건도 함께 설계

2. 5축으로 시나리오 스캔

축명세 / 예시
Happy-path의도대로 동작하는 주요 end-to-end 시나리오
입력/데이터 변형경계값, 일반값, 의미 있는 조합
에러/실패 조건잘못된 입력, 누락 데이터, 타임아웃, 권한, 연동 실패
연동/외부 시스템다른 서비스, 모델 추론, 스토리지, 백엔드 응답 기반 UI 갱신
Frequency/반복빈번 실행, 배치/스케줄, 피크 타임 시 안정성

3. 양보다 질 — 억지로 채우지 않기

에이전트가 형식적으로 TC를 찍어내는 것을 막기 위해 출력량 규칙을 명확히 정의했습니다.

  • 기본 목표: 티켓당 3개 (happy-path 1 + 핵심 회귀 1 + 인접/예외 1)
  • 축소: 단순 버그(텍스트 수정, 좁은 정규식 보정)는 1~2개로 마무리 가능
  • 확장: Corrective Action이 여러 기능 영역에 걸치거나, Frequency가 Always이고 부하 케이스가 본질일 때
  • 금지: 형식적 happy-path나 의미 없는 변형으로 빈자리 채우기
시트에 넘기기 애매한 보조 검증 아이디어는 시트가 아닌 코멘트의 “추가로 검증되어야 할 점” 블록에 담아 시트와 코멘트의 역할을 분리했습니다.
3단계 쓰기 구조와 실제 결과Sheets → 코멘트 → Related TC

Step 1. Google Sheets 기록 (정본)

14컬럼 양식으로 시트 마지막 행 다음에 직접 기록합니다. Agent가 추가한 행은 주황색 배경으로 칠해 사람이 작성한 TC와 즉시 구분되도록 했고, wrapStrategy: WRAP을 적용해 셀 안 줄바꿈이 실제로 보이도록 했습니다.

Step 2 · 3. 코멘트 게시 → Related TC 연결

TC 표는 코멘트에 넣지 않고 TC는 시트가 정본이라는 원칙을 지킵니다. 코멘트에는 간단 분석 · 추가 검증 포인트 · 관련 엣지 케이스 · 시트 추가 위치만 들어갑니다. 생성한 TC_ID는 티켓의 Related TC 필드에 기존값 보존한 채 append해 양방향 추적성이 자동으로 남습니다.

이는 제가 설계한 QA 워크플로우의 세 번째 원칙(Root Cause 의무화)에서 끝나지 않고, 그 기록이 검증 자산으로 이어지는 고리를 만드는 단계입니다. → 01 프로세스 설계
안전장치와 구현 중 마주친 문제들근거 없이 쓰지 않는 구조

안전장치

  • 미리보기 모드 — “초안만 보여줘”라고 하면 시트·코멘트·필드 갱신을 모두 생략하고 화면에만 출력
  • 부분 거부 수용 — “시트에 쓰지 마” 같은 지시를 개별 처리, 거부된 단계 이후는 자동으로 함께 생략
  • fallback 시트 탐색 — 기본 시트 접근 불가 시에만 후보를 제시, 확정 안 되면 쓰기 전체 보류
  • 필드 있을 때만 갱신 — Related TC 필드가 없으면 생성하지 않고 건너뛰기
  • 쓰기 후 검증 — 같은 범위를 다시 읽어 실제 들어간 행 번호·TC_ID 범위를 확인

구현 중 마주친 실제 문제들

🐞 Sheets API가 잘못된 위치에 행을 넣는 문제

드롭다운·조건부 서식이 걸린 빈 영역이 있으면 API가 그 영역까지를 “테이블”로 인식해 마지막 데이터 행에서 10~20행 떨어진 곳에 행을 박아버렸습니다.

→ add_rows를 포기하고, 마지막 데이터 행 + 1부터 시작하는 명시적 셀 범위를 계산해 직접 쓰도록 설계 변경.

📝 코멘트가 마크다운을 렌더링하지 않는 문제

마크다운으로 쓰면 **강조**·## 헤더·- 불릿이 모두 글자 그대로 노출되었습니다.

→ 마크다운 전면 금지로 규칙을 바꿔, 제목은 대괄호, 불릿은 가운데점, 강조는 ALL CAPS: 패턴으로 plain text에서도 시각 구조가 남도록 재설계.

🔢 TC_ID 체계를 “추측”하지 않음

시트 마지막 행의 TC_ID를 먼저 읽고, 그 형식을 유지한 채 일련번호만 증가시킵니다. 순수 숫자면 +1, 접두어가 있으면 접두어 유지. Agent가 출처·형식을 마음대로 만들지 않도록 제약하는 것이 핵심이었습니다.

💡 이 작업이 보여주는 것

  • 정책 설계자와 도구 빌더가 같은 사람 — RCA 의무화 정책을 만든 사람이 그 데이터를 쓰는 도구를 만든 일관성
  • AI를 도구가 아닌 워크플로우 구성원으로 설계 — 프롬프트 래퍼가 아니라 게이팅·안전장치를 포함한 시스템
  • QA 사고 과정 자체를 명문화 — 5축 스캔, RCA 기반 설계, 양보다 질 원칙
사내 확산 — 내 도구에서 팀의 사례로타 팀이 개선 사례로 공유

만들어 쓰는 것과 조직이 받아들이는 것은 다른 문제입니다. 이 에이전트는 제가 홍보한 것이 아니라 다른 팀이 사내 개선 사례로 소개하면서 알려졌습니다.

확산을 염두에 두고 만든 것들

  • 한 줄 호출 — 설정·플래그 없이 기본 시트에 기록되도록 기본값을 잡음
  • 결과가 눈에 보이게 — 주황색 행, 티켓 코멘트, 필드 연결. “돌렸는데 뭐가 달라졌는지 모르겠다”가 없도록
  • 사용 가이드 동봉 — 할 수 있는 일 · 기본 사용법 · 옵션을 사내 문서로 함께 배포
이 반응이 의미하는 것
· 도구가 QA 팀 밖에서도 이해 가능한 형태였다는 것
· AI 활용이 개인 실험이 아니라 팀이 따라 할 수 있는 사례가 됐다는 것
· 같은 맥락에서 QA Request 봇도 함께 언급됨 — 단발성이 아니라 반복적으로 도구를 만들어 온 사람으로 인식됨
돌아보며 좋은 도구를 만드는 것보다 남이 쓰게 만드는 것이 훨씬 어렵다는 걸 테스트 러너와 이 에이전트에서 반복해서 배웠습니다. 그래서 이제는 도구를 만들 때 사용 가이드와 첫 실행 경험을 같은 작업으로 취급합니다.
