테스트 러너 — 모두가 검증할 수 있는 환경

전사가 같은 제품을 만들고 있는데, 그 제품을 검증할 수 있는 사람은 몇 명뿐이었습니다. 만드는 사람이라면 누구나 자기가 바꾼 것을 직접 확인할 수 있어야 한다고 봤습니다. 그래서 설치도 명령어도 없이 브라우저만 있으면 검증이 돌아가는 환경을 만들었고, 설계 · 구현 · 사용자 문서화까지 단독으로 진행했습니다.

Problem

같은 제품을 함께 만드는데 품질 확인은 QA를 거쳐야만 이뤄졌습니다. 스위트는 완성됐지만 터미널·환경 설정을 아는 사람만 돌릴 수 있었습니다.

Action

“도구를 모르는 사람이 눌러도 잘못될 수 없다”를 기준으로, 안전한 기본값과 자동 의존성 해결을 갖춘 검증 환경을 만들었습니다.

Result

만든 사람이 자기가 바꾼 것을 직접 검증하고, QA는 무엇을 어떻게 검증할지 설계하는 데 집중합니다.

제가 만들고 싶었던 것 — 전사가 하나의 제품을 만들고 있다면 만드는 사람 누구나 자기가 바꾼 것을 확인할 수 있어야 하고, QA가 할 일은 그 확인을 가능하게 만드는 것이라고 봤습니다. 검증을 QA가 독점하면 품질은 QA의 처리량만큼만 좋아지지만, 검증할 수 있는 사람이 늘면 품질이 팀 전체의 일이 됩니다.

제 목표는 도구 하나가 아니라 그런 검증 환경을 구축하는 것이었고, 이 러너는 그 일환으로 만들었습니다.
환경은 도구 하나로 만들어지지 않습니다 — 누구나 검증하려면 세 가지가 함께 있어야 했습니다.
· 실행 — 설치·명령어 없이 돌릴 수 있는가 (이 러너)
· 해석 — 결과를 보고 스스로 판단할 수 있는가 (리포트 설계 · 아래)
· 축적 — 결과가 이력으로 남아 다음 판단의 근거가 되는가 (Test Run 관리 도구)
설계 판단 6가지 — 화면에 드러난 결정과 그 이유실제 운영 중인 화면

1. 막되, 막는 이유를 함께 준다

공유 계정 제약은 없앨 수 없으므로 동시 실행을 차단하되, 차단이 “고장”으로 보이지 않도록 누가 · 무엇을 · 몇 분째 돌리는지를 같은 화면에 노출했습니다.

왜 이렇게 사용자가 기다릴지 물어볼지를 스스로 판단할 수 있으면 차단은 장애가 아니라 정보가 됩니다. 도구에 대한 신뢰는 되는 기능이 아니라 안 될 때의 설명에서 갈린다고 봤습니다.

2. 선행 의존은 사용자가 아니라 러너가 안다

프로라벨을 검증하려면 모델이 먼저 학습돼 있어야 합니다. 이 의존 관계를 사용자가 알아야 한다면 셀프서비스가 아니므로, 러너가 선행 테스트를 자동으로 선택하고 🔒로 표시합니다. 마우스를 올리면 무엇 때문에 포함됐는지까지 나옵니다. 1건을 체크하면 16건이 선택됩니다.

왜 이렇게 자동으로 채우기만 하면 “왜 16건이지?”라는 불신이 생깁니다. 자동화하되 근거를 열어두는 쪽을 택했습니다.

3. 예상 시간은 실제 실행 모델을 반영한다

선택 건수와 예상 소요 시간을 즉시 계산하되, 단순 합산이 아니라 3-worker 병렬이라는 실제 실행 방식을 반영한 값을 씁니다. 환경과 언어를 바꾸면 대상 테스트케이스 목록 자체가 함께 갱신됩니다.

왜 이렇게 어긋난 예상치는 한 번만 틀려도 다음부터 아무도 보지 않습니다. 보여줄 수 없으면 안 보여주는 게 낫고, 보여줄 거면 맞아야 합니다.
위 실행에서 예상 1시간 33분 → 실제 1시간 25분 34초.

4. 환경이 못 하는 일은 비활성화가 아니라 감춘다

옵션은 세 개로 줄이고 기본값 그대로 실행해도 문제가 없도록 정했습니다. 화면이 없는 서버에서는 브라우저 창을 띄울 수 없으므로 해당 옵션을 회색 처리하지 않고 아예 감춥니다.

왜 이렇게 고를 수 없는 선택지를 보여주는 것 자체가 혼란입니다. Slack 전송을 opt-in으로 둔 것도 같은 이유로, 부분 실행이 팀 채널을 오염시키지 않게 하기 위해서입니다.

5. 실행 세션은 서버에, 브라우저는 뷰어일 뿐

진행률은 “끝난 수 / 전체”와 현재 테스트를 함께 보여주고, 실행 로그는 실시간 스트리밍됩니다. 창을 닫았다 다시 열어도, 다른 사람이 시작한 실행에 접속해도 로그와 진행률이 그대로 복원됩니다.

왜 이렇게 학습이 포함되면 실행이 수십 분을 넘깁니다. 그동안 브라우저를 켜 두라고 요구하는 순간 사람들은 다시 안 씁니다. 중단하더라도 이미 끝난 테스트의 결과는 보존됩니다.

6. 결과는 서버가 아니라 내 PC로 떨어진다

실행이 끝나면 결과 리포트 열기 · 스크린샷 zip 내려받기 두 버튼이 나타납니다. 서버에서 실행해도 내려받기는 로컬로 떨어지고, 새로고침하거나 나중에 다시 열어도 직전 실행 결과는 계속 회수할 수 있습니다.

왜 이렇게 결과가 실행한 사람 손에 남지 않으면 “돌렸다”로 끝나고 공유·후속 조치로 이어지지 않습니다. 버튼을 실행 중에는 숨긴 것도 미완성 리포트를 배포하는 사고를 막기 위해서입니다.
리포트 설계 — 통과한 것도 “무엇을 봤는지”를 남긴다flaky를 별도 상태로

자동화의 결과물이 PASS/FAIL 숫자로만 끝나면, 사람은 그 숫자를 검증할 방법이 없습니다.

각 테스트의 검증 포인트를 펼치면 무엇을 어떤 순서로 확인했는지가 나오고, 줄 끝의 “화면”을 누르면 그 시점 스크린샷이 열립니다. 통과한 테스트에도 동일하게 붙습니다.

실패 항목은 그 시점 화면이 리포트 파일 안에 들어 있습니다. 링크나 별도 첨부 없이 리포트 하나만 전달해도 상대가 그대로 볼 수 있습니다 — 개발자에게 재현 요청을 넘길 때의 왕복을 줄이기 위한 설계입니다.

상태를 네 가지로 분리한 이유

표시뜻취급
완료검증을 통과정상
실패기대 결과와 다름 — 사유와 화면이 함께 제공원인 확인
불안정재시도해서 통과초록이 아님 · 확인 필요
건너뜀선행 실패 또는 중단으로 미실행선행 결과부터 확인
왜 네 가지로 나눴나 “재시도해서 통과했으니 통과”로 넘기면 flaky가 영원히 쌓입니다. 불안정을 별도 상태로 분리해, flaky를 운이 아니라 원인 있는 결함으로 다루는 기준을 도구 차원에서 고정했습니다.
도구와 함께 만든 사용자 문서 · 결과배포만으로는 아무도 쓰지 않는다

화면 순서를 그대로 따라가는 가이드를 도구와 함께 작성했습니다.

  • 사용자의 언어로 쓴다 — “헤드리스”, “동시성 락” 대신 “창 띄우기”, “지금 다른 실행이 진행 중입니다”
  • 막히는 화면을 미리 설명한다 — 실행이 차단되는 화면을 스크린샷과 함께 보여주고 “이건 고장이 아닙니다”라고 먼저 말해 문의 자체를 줄임
  • 문의가 들어올 지점을 먼저 답한다 — 실패가 많이 날 때 / 예상보다 오래 걸릴 때 / 리포트가 안 열릴 때를 트러블슈팅 섹션으로 선제 정리
  • 문서를 화면에 종속시킨다 — 실제 화면 캡처를 그대로 담고, 화면이 바뀌면 문서도 함께 갱신하는 것을 전제로 구성
이 문서 자체가 산출물입니다. 도구를 만든 사람이 문서까지 책임지지 않으면 결국 문의가 다시 그 사람에게 돌아오고, 병목은 형태만 바꿔 유지됩니다.

이 작업에서 보여준 방식
· 검증을 나눠 갖는 구조를 만든다 — 품질 책임을 QA에 몰아두지 않고, 만든 사람이 직접 확인하게
· 자동화는 돌아가는 순간이 아니라, 남이 쓸 수 있을 때 끝난다 — 실행 UI와 사용자 문서를 자동화의 일부로 봄
· 막을 땐 이유를 함께 준다 — 없앨 수 없는 제약이라면 최소한 판단할 정보를 준다
· 도메인 지식이 필요한 부분은 도구가 대신 계산한다 — 선행 의존, 병렬 소요 시간
· 기준을 문서가 아니라 도구에 고정한다 — 불안정 상태 분리로 flaky 판정 기준을 강제
