MLOps 파이프라인 무인 회귀 검증

데이터셋 업로드부터 7종 AI 모델 학습·배포까지, 비전 AI 학습 플랫폼의 전체 파이프라인을 Playwright로 자동 검증하는 회귀 시스템을 1인으로 설계·구축·운영하고 있습니다.

Problem

릴리스마다 수동으로 하루 이상 걸리던 회귀 검증. 실서버 · 단일 공유 계정 · 30분~3시간짜리 학습이라는 제약까지 걸려 있었습니다.

Action

제약을 먼저 정의하고, 테스트가 서로를 깨뜨리지 않는 구조를 설계했습니다.

Result

명령 한 줄 무인 실행 + Slack 자동 보고. 스위트가 2배 이상 늘어나는 동안 아키텍처는 다시 쓰지 않았습니다.

먼저 제약을 정의했다 — 아키텍처의 모든 결정이 여기서 나왔습니다5가지 제약

테스트를 짜기 전에 이 제품이 자동화에 무엇을 허용하지 않는지부터 정리했습니다.

제약그래서 무엇이 어려워지는가설계로 답한 방식
산출물의 소속
모든 노드는 자기 프로젝트 안에서만 유효		 고정 프로젝트를 재사용하면 실행할 때마다 노드가 쌓여 결국 깨진다 테스트마다 전용 프로젝트 생성 → 종료 시 삭제를 공용 헬퍼로 강제
실서버 대상
목(mock) 없이 3개 실환경		 실패를 임의로 만들 수 없고, 서버 상태가 결과에 개입한다 서버 정책을 실험으로 규명해 전제로 삼고, 장애는 요청 차단·주입으로 재현
단일 공유 계정 + SSO 동시 로그인이 앞 세션을 끊어 병렬 실행이 성립하지 않는다 세션 단위가 계정이 아니라 기기(User-Agent)임을 규명 → worker별 UA 분리
고비용 작업
모델 학습 30분~3시간		 소비 테스트마다 재학습하면 스위트를 운영할 수 없다 학습 결과를 픽스처에 기록해 재사용 — 타입당 1회로 고정
비동기 장기 작업
완료 신호가 일시적 UI		 토스트를 기준으로 삼으면 부하 시 false PASS가 난다 노드 상태 · 다운로드 파일 · 요청 페이로드를 판정 근거로
화면이 아니라 데이터를 단언한다 — 리포트 검증은 화면 표시만 보지 않고 다운로드한 zip을 파싱해 서버 원본 값과 대조합니다. 이미지 수 · 모델 사이즈 · Threshold가 UI · 파일 · 요청 페이로드 세 곳에서 일치하는지 확인합니다. “떠 보이는 것”과 “실제로 된 것”을 구분하는 것이 판정 기준입니다.
병렬 실행 — 단일 계정 실서버에서 성립시키기핵심 난제

🔑 worker별 User-Agent 분리

SSO가 “같은 UA 동시 로그인 = 같은 기기 재로그인”으로 앞 세션을 끊는 것을 실험으로 규명하고, worker마다 UA 토큰을 부여해 3-worker 동시 로그인 성립.

⚡ 파일 내 병렬

단일 직렬 전처리 스위트를 3그룹으로 분할, 각 그룹이 전용 프로젝트를 갖고 worker에 분산.
19.3분 → 11.8분 (-39%)

🧮 서버 정합

서버 동시 작업 상한(3)에 맞춰 worker 수와 대기 정책을 정합, 완료 대기 한도를 “최장 학습 잔여 + 여유”로 산정해 큐 대기 오탐 제거.

버린 것도 기록합니다 세션 문제 우회용으로 만들었던 탭 orchestration 구조는 단일 실패점이므로 폐기했습니다. 더 단순한 정답이 나오면 이미 만든 것도 버립니다.
트러블슈팅 — 증거로 원인을 확정한 5건추측으로 고친 것은 없습니다

CASE 1 — 로그인은 됐는데 로그인 화면으로 돌아온다

로그인 직후 goto로 끼어들면 SSO 리다이렉트 체인이 끊겨 미인증이 됨을 단계별 URL 진단으로 확정. 이동을 금지하고 자동 도달만 대기하도록 변경, 신/구 로그인 방식을 자동 분기해 3개 환경이 한 헬퍼를 공유.

CASE 2 — “수동은 되는데 왜 자동화만 안 되지?”

“계정당 단일 세션”이라는 그럴듯한 가설에 머물지 않고 모순을 실험으로 파고들어, 세션이 계정이 아니라 기기 단위임을 규명. cloud 병렬 1 → 3 worker 복구.

CASE 3 — 6분짜리 학습이 26초 만에 “완료”

통과한 TC가 범인인 케이스. 리포트 타임라인 재구성 + DOM 스냅샷으로 준비 구간이 부하에서 길어져 완료 판정을 오판함을 확인. 진행 토스트를 판정에 추가해 전 구간 보호.

CASE 4 — 캔버스가 하얗게 비는 글리치

trace DOM 스냅샷 추적으로 React Flow의 인라인 visibility:hidden 고착을 확인, 트리거(모달 닫힘 직후 소켓 알림)까지 특정. 단독 재현 스크립트를 제작해 제품 버그로 리포트.

CASE 5 — 40초가 모자라서 실패한 검증

“재현 안 되는 flaky”를 전체 테스트의 시작/종료 시각으로 서버 슬롯 점유를 재구성해 규명 — 코드 버그가 아니라 구조적 대기. flaky를 “운”이 아니라 원인 있는 결함으로 다뤘습니다.

🔍 공통 접근

  • trace DOM 스냅샷 시점별 추적
  • 리포트 타임라인 재구성
  • 요청 페이로드 가로채기
  • 단독 재현 스크립트 제작
  • 가설과 모순되는 사실을 끝까지 파고들기
리포팅과 성과 — 결과가 팀에 도달해야 자동화가 완성된다커스텀 Slack 리포터 자작
  • 경량 첨부 설계 — video·trace 제외 zip만 첨부(수 GB → 1~2MB), 로컬에는 전체 아티팩트를 실행별 폴더로 보존
  • 대화형 실행기 — 명령 한 줄로 테스트명·Slack 전송 여부를 묻고 실행. CI에서는 무질문 자동, 부분 실행이 팀 채널을 오염시키지 않도록 전송은 opt-in
  • 보안 — trace에 평문 기록되는 자격 증명을 인지하고 계정 정책·gitignore·첨부 제외로 노출 경로 차단

스위트 확장추가할수록 구조 수정 필요규모 2배 이상 확장 · 아키텍처 무변경
검증의 질문기능이 도는가+ 결과 품질이 유지되는가 · 고친 것이 유지되는가
확장 비용을 낮추는 설계 — 초기 구축 이후 모델 성능 비교 · 회귀 테스트 영역이 더해지며 스위트 규모는 두 배 이상이 됐습니다. 그때 한 일은 구조를 고치는 것이 아니라 기존 구조 위에 스위트를 얹는 것이었습니다. 자동화의 진짜 비용은 처음 만들 때가 아니라 늘려갈 때 발생하기 때문에 그 지점을 먼저 설계했습니다.
이 프로젝트에서 보여준 방식
· 증거로 원인을 확정한다 — trace DOM 스냅샷, 리포트 타임라인 재구성, 요청 페이로드 가로채기
· 가설은 실험으로 깬다 — 그럴듯한 결론에 안주하지 않고 모순을 파고들어 진짜 정책을 찾는다
· 더 단순한 답이 나오면 버린다 — 동작하던 구조도 단일 실패점이면 미련 없이 폐기
· 실패를 설계한다 — 제품 버그는 실패하는 테스트로 고정해 추적하고, 의존 그래프로 실패 전파를 차단
