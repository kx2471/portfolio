QAプロセスを0から1へ

課題管理の仕組みがなかった環境に、ワークフロー・Priority基準・Root Causeの記入必須化・デプロイゲート・RC検証手順を自ら設計し、ルールが実際に機能するよう自動化まで組み込みました。

Problem

優先度は起票者の主観に任され、不具合の原因は記録されず、未検証のビルドが現場にデプロイされる事故もありました。

Action

判断基準を明文化し、守られなければ自動で差し戻すルールをトラッカーに設定しました。

Result

「これ、QAに回していいですか？」がフィールドの条件に置き換わり、デプロイを差し止める権限がQAに明示的に与えられました。その後のリリースは、TC 185件・Pass率97.3%（基準95%）、Urgent・High 0件で判定しました。

判断と貢献

役割 · ワークフロー・Priority・RCA・デプロイゲート・RC手順の設計と導入を主導、自動化ルール・QA Requestボット・Test Runツールを実装

  1. 未検証ビルドのデプロイ事故を、個人のミスではなく仕組みの空白と捉えました。 — バージョンラベルだけでデプロイ対象を確認する限り、同じことは誰がやっても再び起きます。そこで責任追及ではなく、ビルド番号基準のデプロイゲートをつくりました。
  2. QAにはNO-GOの差し止め権を、最終的なGOはPMに置きました。 — QAがビジネス判断まで抱えると、品質の報告が交渉になります。品質の事実の報告とデプロイの決定を分けました。
  3. Root Causeフィールドを必須化する前に、不具合272件を全件分析しました。 — 自由記述のRoot Causeの43%が1行だけでした。最初は反発もありましたが、この数字と実際のチケットから抽出した10カテゴリーで説得して必須化しました。今ではこのフィールドがイシュー分析・インサイト導出・バグ予防の入力になっています。
  4. ルールをドキュメントではなくトラッカーの自動化に組み込みました。 — RCA未記入のまま進めると自動で差し戻します。人の注意に頼るルールは、忙しいときに真っ先に破られます。
開発・QAワークフロー — コードの流れと仕事の流れをつなぐGit × 課題トラッカー × Automation

設計した全体の流れ

ブランチ作成Gitイベント
→
In Development自動で遷移
→
In ReviewPR · Fix Versionを記入
→
Dev Completeバージョンブランチへマージ
→
In QARCA記入 + Version確認
→
Resolved修正完了
→

最後の扉はQAが閉じる — Resolvedは開発が「直した」と宣言した状態にすぎません。 QAが最終確認して初めてClosedに進みます。 チケットを開く人と閉じる人を分け、「直した」という申告と「直っている」という確認が混ざらないようにしました。
差し戻しの道も設計 — 検証で差し戻すとIn QA → In Developmentに戻ります。 RCA未記入のままDev Completeにしようとすると、Automationが自動でIn Developmentに戻します。

送信後 — 約束が守られるかまで見守る

チケットをつくって終わりにしない

ボットがreleaseチャンネルのJenkinsのビルドメッセージを監視し、 チケットに書かれたバージョンのRC1ビルドが上がったかを自ら確認します。 予定時刻を過ぎても見つからなければ警告 + 関係者へのメンション、2時間おきの再通知、 24時間後に自動終了。

状況素朴につくると実際の設計
日付を初めて設定変更とみなして通知通知しない — 変更・削除のときだけ
開始日と期日を同時に変更通知が2件1件にまとめる
予定時刻より前にデプロイ予定時刻まで待つ確認次第すぐ✅で完了
未デプロイが続く1回警告して放置2時間おきに再通知
いつまでも出てこない無限に繰り返す → 通知疲れ24時間後に自動終了
デプロイ日が変更された古い時刻を基準に誤検知1分以内に検知 → 新しい基準で再始動
チケットが削除された孤立したリマインダーが鳴り続ける1分以内に自動で片付ける
判定ルールのないプロダクト誤検知の通知チケットのみ作成 · リマインダーは動かさない
ここで学んだこと 通知システムの本当の難しさは「いつ送らないか」にあります。 自動通知はつくるのは簡単ですが、嫌われるのも簡単です。チームにボットを止められないようにすることが設計の目標でした。
デプロイゲート — QAのNO-GO差し止め権インシデントから生まれたプロセス

未検証のビルドが顧客の現場にデプロイされるインシデントがありました。原因を追うと、個人のミスではなく 仕組みの空白でした — デプロイ対象の確認がバージョンラベルだけで行われ、 QAの検証完了とデプロイの決定の間に明示的なつながりがなかったのです。

1. ビルド成果物の一致バージョンラベルではなくビルド番号単位
→
2. QA検証完了のチェックデプロイの前提条件
→
3. 開発チームの承認
→
4. PMの最終GOデプロイの決定権限
権限を分けました — QAは品質の状態を報告し、NO-GOでデプロイを差し止めることができ、 GO/NO-GOの最終決定はPMに置きます。品質を報告する責任とデプロイを決める権限が混ざらないようにした設計です。
例外をプロセスの中へ — 緊急デプロイを認めないプロセスは迂回されます。 緊急レーンを別に設けたうえで、リスク受容の承認・未検証範囲の文書化・事後QAの義務化を付けました。

インシデントを責任追及ではなくプロセス改善に転換し、 QAがリリースパイプラインの形式的な参加者ではなく、明示的な権限を持つゲートキーパーになりました。

RC検証手順 — 「いつ終わるか」を数字でExit Criteria · 役割の分離

「状況によって毎回違う」進め方だったRC検証を、繰り返し使える手順として確立しました。 QAの検証と開発の修正を並行させ、準備ができ次第デプロイ（上限は1営業日以内）して早期に収束させます。

RC1Full Test · 全テストケース
→
課題の修正Urgent→Highの順
→
RC2Retest + Regression
→
RC3検証
→
リリース判定PM GO / NO-GO
Exit Criteria基準
残存Urgent0件（最優先のゲート）
残存High5件未満（1件ごとにPM・PLと協議）
Pass Rate95%以上
Normal / Low個別のゲートは設けずPass Rateに含める → Known Issueとして管理

個々の案件で毎回議論する代わりに、数字で判定できる基準を定義して判定コストを下げました。 QAは基準を満たしているかを報告し、GO/NO-GOの決定はPMが行います — QAがビジネス判断を抱え込まず、品質の事実に集中できるようにするための分離です。 本番の緊急修正は、Full Testを省いて自動化による迅速な検証だけを行うHotfix専用トラックに分け、 緊急対応が通常の手順を崩さないようにしました。

QA Test Run管理ツール — 結果を1つの履歴にGoogle Sheets + Apps Script

バージョンごとにマスターシートからテストケースをコピーし、結果を各バージョンのシートに散らばって記録していたため、 「このテストケースはバージョンを経てどうなったか」を見るには複数のシートを目で追う必要がありました。 回帰対象の選定・バージョン別のサマリー・トレーサビリティの根拠づくりも、毎回手作業でした。

マスターTC要件と連携
→
Test Runシート実行 · 結果入力
→
Test Run History蓄積 · 参照の元データ
貯める場所と見る場所の分離 — Historyは結果を縦に積み続ける元データで、 人はその上に載せた参照ビューで見ます。 DBの元テーブルを直接探さず、クエリで参照するのと同じ構造です。

回帰の引き継ぎ — RC2のつくり方

ソースを既存のTest RunシートのRC1にし、フィルターをP/F = FAIL, NAにすると、 RC1で失敗した、または未検証の項目だけがP/F空欄のまま引き継がれます。 RC検証手順の「Retest + Regression」を、手作業ではなくツールが計算します。

問い答え方

回帰対象 — 過去にFAILしたテストケースは？Historyのフィルター / 引き継ぎ作成

定着まで設計 自動入力のトリガーはスプレッドシート自体にインストールされており、誰が編集しても動作します。 メンバーが各自で有効にする必要はありません。ツールを配ることと、チームに実際に使ってもらうことは別の問題です。
根本原因分析 — 原因が蓄積される仕組み全件レビュー · 10カテゴリー

不具合チケットは増える一方で、根本原因は自由記述で散らばるか、まったく記録されていませんでした。 「どの種類の原因が繰り返されているか」に定量的に答えられる人はおらず、 構造化したフィールドの導入を提案しても説得材料がありませんでした。

導入前の基準（1つのリリースライン）数値
不具合272件 — うちreopen 17件・運用イシュー18件
自由記述のRoot Cause43%が1行だけ — 後から原因を分析し直せない水準
自由記述 · 未記録集計できない
→
全件分析（272件）帰納的に10カテゴリーを導出
→
選択式フィールド + 記入の必須化Automationで強制
→
原因分布の自動蓄積以後すべての不具合がデータになる

反発と説得

最初に必須化を持ち出したときは反発がありました。 そこで意見ではなく数字で話しました — 今のやり方で書かれた原因の43%が1行だけで、後から誰も分析し直せないこと、 実際のチケットをまとめると原因が10の類型で繰り返されていること。この根拠で説得して必須化し、 今ではこのフィールドがイシュー分析・インサイト導出・バグ予防に使われています。

272件は出発点にすぎません。 分析時点の件数は増え続けますし、それこそがこの仕組みの狙いです。 目的は一度きりの正確な集計ではなく、 不具合が増えていく間も、原因の分布が自動で最新に保たれることでした。

サンプルではなく全件を見ました。分類体系を先に決めてチケットを当てはめたのではなく、 実際のチケットから繰り返しのパターンを抽出してカテゴリーをつくったため、現場の不具合の傾向がそのまま反映されています。

このデータの行き先

  • 品質状況報告の定量的な根拠 — 繰り返し発生する原因の上位カテゴリーから改善の優先順位を導出
  • 定期トリアージ・Known Issueバックログ管理の基礎データ
  • 回帰テストケースの入力 — 最初はTC Creatorが、今はQA Vaultがこのフィールドを読んで回帰テストケースを設計 → CASE-06 · CASE-01
  • インサイト・バグ予防 — 繰り返す原因を一文の原則として蓄積し、次の機能のテスト観点として再利用
要点 — 「提案する前に全件を見る」という姿勢。 フィールドを1つ追加するような小さなプロセス変更でも、データの根拠をもとに提案すれば組織の受け入れの速さが変わります。
