AI Agent — Regression TC Creator

私が記入を必須化したRoot Causeの記録を読み取り、回帰テストケースを設計してGoogle Sheetsに記録し、チケットにコメントとフィールドまで連携するClaudeベースのAgentです。ルールを定めた本人が、そのルールが残したデータを活用するツールを自らつくりました。

Problem

RCAの記録は溜まる一方で、活用されない資産になるおそれがあり、回帰テストケースの設計・記録・連携は毎スプリント繰り返す手作業でした。

Action

MCPツールの組み合わせ・3段階のゲーティング・安全策を備えた仕組みとして実装しました。

Result

チケットIDを1行渡すだけで、テストケース設計・シートへの記録・チケット連携が自動で完了します。Related TCで紐付いた回帰資産は45件、他チームが社内の業務改善事例として共有しました。

判断と貢献

役割 · 設計・実装・社内展開を単独で担当

  1. 私が必須化したRoot Causeの記録が死んだデータにならないよう、その使い道を自らつくりました。 — 使われない記録は、やがて書かれなくなります。
  2. シートへの記録 → コメント → フィールド連携を、前の段階が成功しないと進まない3段階にまとめました。 — 一部だけ反映された不完全な状態が、最も見つけにくいエラーだからです。
  3. レビュー用のシートを別に設けず、正本に直接書き込むようにしました。 — シートが2つあると誰も見ません。代わりにオレンジ色の背景・作成者をClaudeに固定・空の分類欄で、まだ人が見ていないテストケースが正本の中で分かるようにしました。
  4. その後、ツールからナレッジベースへと移行しました。 — 現在はこのエージェントではなくCASE-01のナレッジベースを根拠に回帰テストケースを書き、レビューは目印ではなく関門（下書き → レビュー → 作成）になりました。
なぜつくったか · 動作の流れルールが残したデータを使うツール

QAワークフローを設計する中で、不具合チケットのRoot Cause・Corrective Actionの記入を必須化しました。 しかしこの情報は記録されるだけで活用されない資産になるおそれがありました — 毎スプリント、不具合チケットを1件ずつ読み、回帰テストケースを手で設計し、シートに記録し、 元のチケットに紐づける作業は単純作業の繰り返しでした。

3つの書き込みは、前の段階が成功して初めて次に進みます。 一部だけが反映される中途半端な状態を根本から防ぐためです。

実際の動作 — チケット1件で最後まで

呼び出しは1行で済む

エージェントをサブエージェントとして登録しておき、チケットIDを1つ自然言語で渡すだけです。 設定やオプションのフラグなしでデフォルトのシートに記録されるよう初期値を決め、 使う人が毎回決めることをなくしました。

なぜこうしたか ツールが使われるかどうかは、機能の数ではなく最初に使うときの手間で決まります。 「何を設定すればいい？」と一度でも思わせたら、人は手作業に戻ります。
設計原則 — QAエンジニアの思考プロセスを明文化RCAベース · 5軸のスキャン · 量より質

1. RCAに基づくテストケース設計

チケットを要約するのではなく、過去の失敗モードを再現することを行います。

  • Root Causeが明記されている場合 → その失敗モードを再現する明示的なケースを設計
  • Corrective Actionが実際に防げているかを確認する回帰ケースを追加
  • 同じ根本原因の影響を受けうる隣接する境界条件も合わせて設計

2. 5つの軸でシナリオをスキャン

軸内容 / 例
Happy-path意図どおりに動く主要なエンドツーエンドのシナリオ
入力・データの変化境界値、通常値、意味のある組み合わせ
エラー・失敗条件不正な入力、欠損データ、タイムアウト、権限、連携の失敗
連携・外部システム他のサービス、モデル推論、ストレージ、バックエンドの応答に基づくUI更新
Frequency・繰り返し頻繁な実行、バッチ・スケジュール、ピーク時の安定性

3. 量より質 — 無理に埋めない

エージェントが形だけのテストケースを量産しないよう、出力量のルールを明確に定めました。

  • 基本目標：チケット1件につき3つ（happy-path 1 + 主要な回帰 1 + 隣接・例外 1）
  • 縮小：単純な不具合（文言の修正、狭い正規表現の補正）は1〜2つで完了してよい
  • 拡大：Corrective Actionが複数の機能領域にまたがる場合や、FrequencyがAlwaysで負荷ケースが本質の場合
  • 禁止：形だけのhappy-pathや意味のない変化で空きを埋めること
シートに載せるには曖昧な補助的な検証アイデアはシートではなく、 コメントの「追加で検証すべき点」ブロックに入れ、シートとコメントの役割を分けました。
3段階の書き込み構造と実際の結果Sheets → コメント → Related TC

Step 1. Google Sheetsへの記録（正式版）

14列の書式で、シートの最終行の次に直接記録します。 レビュー用のシートを別につくらず正本に直接書き込むのは、意図した選択です — シートが2つあると誰も見ません。 その代わり、正本の中にレビューの仕掛けを設けました。Agentが追加した行はオレンジ色の背景にし、 作成者はClaudeに固定し、分類欄は空けておいてQAが埋めるようにしました。 分類が空のオレンジ色の行が、そのまま「まだ人が見ていないテストケース」です。また、 wrapStrategy: WRAPを適用してセル内の改行が実際に見えるようにしました。

Step 2 · 3. コメントの投稿 → Related TCの連携

テストケースの表はコメントに入れず、テストケースはシートが正式版という原則を守ります。 コメントには簡単な分析・追加の検証ポイント・関連するエッジケース・シートの追加位置だけが入ります。 生成したTC_IDはチケットのRelated TCフィールドに既存の値を残したまま追記し、 双方向のトレーサビリティが自動で残ります。

これは、私が設計したQAワークフローの3つ目の原則（Root Causeの記入必須化）で終わらせず、 その記録が検証の資産へとつながる輪をつくる段階です。 → CASE-03 プロセス設計
安全策と実装中に直面した問題根拠なしには書かない仕組み

安全策

  • プレビューモード — 「下書きだけ見せて」と指示すると、シート・コメント・フィールドの更新をすべて省き画面にだけ出力
  • 部分的な拒否に対応 — 「シートには書かないで」などの指示を個別に処理し、拒否された段階以降も自動で一緒に省略
  • フォールバックのシート探索 — デフォルトのシートにアクセスできないときだけ候補を提示し、確定しなければ書き込みをすべて保留
  • フィールドがあるときだけ更新 — Related TCフィールドがなければ作成せずにスキップ
  • 書き込み後の検証 — 同じ範囲を読み直し、実際に入った行番号・TC_IDの範囲を確認

実装中に直面した実際の問題

🐞 Sheets APIが誤った位置に行を挿入する問題

プルダウン・条件付き書式が設定された空の領域があると、APIがその領域までを「テーブル」と認識し、 最後のデータ行から10〜20行離れた場所に行を入れてしまいました。

→ add_rowsの使用をやめ、 最後のデータ行 + 1から始まる明示的なセル範囲を計算して直接書き込むよう設計を変更。

📝 コメントがMarkdownを表示しない問題

Markdownで書くと**強調**・## 見出し・- 箇条書きが すべて記号のまま表示されていました。

→ Markdownを全面禁止にルールを変え、 見出しは角括弧、箇条書きは中黒、強調はALL CAPS:のパターンで、 プレーンテキストでも見た目の構造が残るよう設計し直しました。

🔢 TC_IDの体系を「推測」しない

シートの最終行のTC_IDを先に読み取り、その形式を保ったまま連番だけを増やします。 数字だけなら+1、接頭辞があれば接頭辞を維持。 Agentが出どころや形式を勝手につくらないよう制約することが要点でした。

社内展開 — 自分のツールからチームの事例へ他チームが改善事例として共有

つくって使うことと、組織に受け入れられることは別の問題です。 このエージェントは私が宣伝したのではなく、他のチームが社内の改善事例として紹介したことで広まりました。

展開を見据えてつくったもの

  • 1行で呼び出し — 設定やフラグなしでデフォルトのシートに記録されるよう初期値を決めた
  • 結果が目に見えるように — オレンジ色の行、チケットのコメント、フィールドの連携。 「実行したけど何が変わったか分からない」とならないように
  • 利用ガイドを同梱 — できること・基本的な使い方・オプションを社内ドキュメントとして一緒に配布
その後 — ツールからナレッジベースへ — 現在はこのエージェントを使っていません。 チケット1件のRoot Causeだけを見るやり方から、QA Vault（CASE-01）に蓄積された仕様・イシュー・インサイト全体を根拠に 回帰テストケースを書くやり方へ移行しました。レビューも目印から関門に変わり、AIが書いたテストケースは下書き → レビュー → 作成を経ます。
振り返って 良いツールをつくることより、他の人に使ってもらうことのほうがはるかに難しいということを、 テストランナーとこのエージェントで繰り返し学びました。 だから今は、ツールをつくるときに利用ガイドと最初の実行体験を同じ作業として扱っています。
