検証実務 — API検証・トレーサビリティ・業務ツール

UIを経由せずAPIを直接叩いてフロントエンドでしか防げていなかった入力チェックとXSSの経路を見つけた事例、要件–テストケース–不具合のトレーサビリティ体制、繰り返し作業を減らすためにつくったツールです。

Problem

UIで弾かれる値がサーバーでも弾かれるかは確認されておらず、要件–テストケース–不具合がばらばらに管理されていました。

Action

APIレベルまで掘り下げて検証し、トレーサビリティの体制を整え、繰り返し作業はツールで減らしました。

Result

サーバー側検証の欠如とXSSの経路を発見して改善を主導し、要件カバレッジと不具合のトレーサビリティを確保。

判断と貢献

役割 · API検証・トレーサビリティ体制の確立・業務ツールの制作

  1. フロントエンドの入力チェックを品質保証とは見なしませんでした。 — 画面で止まったことは、サーバーが止めた証拠ではなく、画面がリクエストを送らなかった証拠にすぎません。
  2. レスポンスコードで止まらず、DBへの保存と管理画面まで追いかけました。 — その先で、保存されたスクリプトが管理画面で実行されるXSSの経路を見つけました。
  3. 発見後に基準を変えました。 — フォームのある機能では、UIでの通過とAPIでの通過を別々の検証項目として扱います。
API検証 — UIの裏側を直接叩くサーバー側検証の欠如を発見

フロントエンドの入力チェックはユーザーへの親切な仕掛けにすぎず、品質保証ではありません。 そこでUIを経由せずREST APIを直接呼び出し、同じルールがサーバーでも守られているかを確認しました。

1. リクエストの取得DevToolsで実際のパケットを抽出
→
2. 構造・認証の分析パラメーター · Cookie · CSRF
→
3. 改ざんしたリクエストPostman · cURL
→
4. 結果の検証レスポンス · DB保存 · 管理画面まで
なぜこうしたか UIの自動化は「弾かれること」しか確認しません。画面で弾かれたという事実は、 サーバーが弾いた証拠ではなく、画面がリクエストを送らなかった証拠にすぎません。

画面を経由しないからこそできること

  • 型・精度の境界をそのまま通してみる — 整数のフィールドに小数を、真偽値に文字列を入れたとき、 サーバーが何を保存するか
  • 到達しにくい状態をつくってから始める — デプロイ状態などの値を直接PUTで設定し、 UIでは何段階も経る前提条件を一度に整える
  • 拒否されるべきリクエストをつくって送る — 認証ヘッダーを外したり変えたりして、 通るケースではなく弾かれるべきケースを確認

発見事例 — フロントエンドでしか防げていなかった入力チェック

手順

  • DevToolsで会員登録・会員情報変更のリクエストパケットを抽出
  • パラメーター構造と認証方式を分析
  • Postman・cURLで形式に違反する値と<script>タグを挿入して送信
  • レスポンスだけでなく、DBへの保存と管理画面への反映まで追跡

発見

  • サーバー側の入力値検証が欠如 — フロントエンドの検証のみ
  • 形式・ルールに違反したデータがそのままDBに保存
  • 挿入したスクリプトが管理画面で実行される経路を確認 → XSS

報告

  • 再現手順をそのままたどれるよう整理
  • スクリーンショットとパケットログを証拠として確保
  • UIの不具合ではなくサーバーの検証ロジックの欠如と原因を特定
  • 改善の方向性まで提案し、修正を主導
画面ベースのテストだけなら最後まで見つからなかった不具合です。 それ以降、フォームのある機能ではUIでの合格とAPIでの合格を別の検証項目として扱っています。
QA成果物 — 要件から不具合まで追跡できるようにSWR · TC · Defect · Xray

Xrayによるトレーサビリティ

要件とテストケースを紐づけてトレーサビリティを確保し、不具合管理との連携で双方向に追跡できます。

  • Requirement Traceability — すべての要件がテストケースに紐づき、充足しているかを判断できる
  • Defect Traceability — 不具合から逆方向に、実行履歴・テストケース・要件まで追跡
  • Test Set（機能別のテストケース管理）・Test Plan（スケジュール）・Test Execution（実行結果）でライフサイクルを一元管理
数より性質 — 「テストケース300件」より「要件の全項目との照合 + 境界値の組み合わせ + 過去の不具合にもとづく重点領域」のほうが 正確な説明です。テストケースごとにどの根拠でつくったかを残し、回帰対象を選ぶときの基準にしています。
