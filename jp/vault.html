QAナレッジ管理システムの構築 — QA Vault

チケット・テストケース・企画書・意思決定に散らばっていたQAのナレッジを、相互にリンクされた一つのナレッジベースに集約し、 AIエージェントが毎朝無人で最新化するようにしました。 ナレッジこそが資産で、AIは道案内役という方針のもと、3.5週間で企画・設計・構築を一人で行い、現在も運用しています。

Problem

バグはClickUp、テストケースはシート、企画はFigma、決定事項はコメント。「この機能の仕様は何だったか」に答えるには4か所を探す必要があり、企画の変更は誰にも気づかれずに過ぎていました。

Action

スクリプトは収集・比較、AIエージェントは判断・整理、人は承認と役割を分け、ナレッジベースと平日09:00の無人同期を構築しました。

Result

イシュー439・テストケース1,372・仕様18・インサイト38が一か所でつながり、企画の変更は翌朝のレポートで影響TCの修正案とともに届きます。

判断と貢献

役割 · 単独で企画・設計・構築・運用（3.5週間、以後運用中）

  1. 収集・比較はスクリプト、判断はAI、確定は人と分けました。 — AIに収集まで任せると、同じ入力でも結果が毎回変わったためです。
  2. 企画の決定を仕様書に自動登録せず、「候補」として挙げるだけにしました。 — コメントを読み違えて誤った仕様が確定すると、その仕様を根拠につくったテストケースまで一緒に誤ります。
  3. 企画担当に新しいツールを求めず、普段書いているコメントを読みに行きました。 — 仕様書が蓄積されなかった原因は、書く場所がないことではなく、書く手間にありました。

インサイトは原子単位で

インサイトノートはファイル名そのものが一文の原則です。 例：「新しいデータ種別が追加されたら、既存の全ノードでその種別の分岐を確認する」。 必ず根拠となるイシュー・プロジェクトをリンクし、根拠の数を数えます。根拠の多い上位10件は累積コンテキストとして保持し、 次の機能のテスト観点として再利用します。

なぜこうしたか 「注意すべきこと」のような長い文書は誰も読み返しません。一文の原則に根拠リンクが付いていてこそ、 人もAIも取り出して使え、根拠の数で重要度を判断できます。

Figmaの企画変更検知

企画書は頻繁に変わるのに、変更の通知はありません。最初に使ったMCPツールは呼び出し上限が小さく、コンポーネント内の文言を読めませんでした。

  • Figma REST APIで表示されるすべてのテキストを抽出し、スナップショットと比較（変更・追加・削除）。ファイルのバージョンが同じならスキップ
  • 同じフレーム内でidだけが変わった文言は相殺して誤検知を削減
  • 仕様ノートには以前の文言を取り消し線で残し、新しい文言を反映して変更履歴を記録
  • テストケースから以前の文言を使っているTCを探し、修正案をレポートで提案 — TCは承認後にのみ修正
  • 企画の説明とデザイン案の文言が異なれば❗ 不一致と表示 → 開発前に企画担当とすり合わせる
成果 — 企画書の変更を翌朝のレポートで把握し、影響を受けるテストケースの修正案まで受け取れます。 古い期待結果でテストしてから「企画が変わっていた」と気づくことがなくなりました。
Human-in-the-loop — 決定は人が確定する仕様登録候補 · レポートへの返信

企画の決定 → 仕様書

企画担当がチケットのコメントだけで決めると、仕様書に残りません。かといって企画担当にGitやObsidianを使ってもらうのはハードルが高すぎます。

企画担当のコメントいつも通りチケットに記入
→
仕様登録候補登録先 · 文 · 矛盾 · 影響TC
→
QAの返答OK / 確定 / 却下
→
仕様書に登録登録された決定は確定

同期処理が企画担当のコメントから仕様の決定と思われる文だけを選び、レポートに挙げます。 自動登録はしません — 誤解によって誤った仕様が確定するのを防ぐためです。

「レポートに返信」— 非同期の承認

レポートの提案の下に形式を問わず自由に返答を書くと、次回の同期が 前回のコミットと比較して人が変更した行だけを見つけ、意図を判断して処理します。

🛡️ プロンプトインジェクション対策

レポートに引用された外部コメントは比較の基準にすでに含まれているため、指示として読まれません。 他の人のコミットが混ざった場合は外部への書き込みを行いません。

✍️ 書き込み範囲の制限

外部への書き込みは許可範囲（TCの作成・修正、関係の紐付け）に限定し、 変更前後の値を残していつでも戻せるようにしました。

なぜこうしたか ユーザーがすでに使っているツールの中で動かなければ使われません。企画担当に新しいツールを求める代わりにコメントを読みに行き、 QAの承認も別画面ではなくレポートに一行書くだけで済むようにしました。
テストケース管理 · カバレッジ · 文書化の自動化下書き → レビュー → 反映
  • TC移行 — スプレッドシートのTC 1,279件をClickUpへ移行し、毎日同期
  • TC作成 — 仕様・要件・過去のバグを根拠に下書き → 人が下書きファイルにレビューメモ → 反映後に一括作成。 例：新機能のTC 36件の下書き → レビューで3件削除・2件修正 → 33件作成、要件との紐付けまで自動
  • カバレッジ — 回帰TCのないバグ、TCのない機能・仕様を自動集計
  • 自動化の追跡 — E2Eコードのテストケースアノテーションと実行レポートを読み、 自動化対象760件中391件（51%）、機能領域別の残り、新しいFailを毎日追跡 （CASE-04）
  • runツール — スプレッドシートのマクロをClickUp用のGUI・CLIとして再実装（条件フィルターでrun作成、完了記録、不具合の紐付け、結果集計）
  • Test Plan · Reportスキル — チームの文書テンプレートを読んで従い、範囲はバージョンのチケット一覧、TCはrun、結果はrun統計・チケットコメントから取得。 PlanとReportを一対で扱い、同じ範囲・合格基準・runを共有し、Planの項目ごとに結果が付く
CASE-06からの発展 — Regression TC Creatorはチケット1件のRoot Causeを読んで正本のシートに直接書き込み、 オレンジ色の行・作成者の固定・空の分類欄でレビューを促していました。現在はそのエージェントの代わりにこのリポジトリの仕様・イシュー・インサイト全体を根拠に 回帰テストケースを書き、AIが書いたTCは下書きファイルにとどまり、人のレビューメモが反映された後にのみ作成されます。

設計原則（ガードレール）

1
作り話をしない
確認されていない動作は❓ 未確認と表示
2
根拠を残す
テストのチェック・仕様・インサイトすべてに出典（チケット・決定・文書）のリンクが必須
3
決定ログは追記のみ
変わった決定は新しい番号で追加し、以前の番号を参照
4
修正ではなく履歴
仕様が変わったら以前の文言を残し、変更履歴に日付と根拠
5
外部への書き込みは承認後
例外は事前に許可を得たフィールド（TCの最新結果など）のみ
6
最終判断は人
インサイトの確定、仕様の登録、TCの作成は人が承認

実装中に直面した問題

🔇 同期が静かに失敗

無人実行中にOAuthが期限切れになったのに、終了コードが伝わらず失敗したことにも気づけませんでした。

→ 終了コードの伝達、リトライ、失敗マーカー + 再ログインされたら15分以内に自動再実行。

🎨 Figmaの構造が一部しか見えない

MCPのメタデータツールの限界と呼び出し上限のため、コンポーネント内の文言が読めませんでした。

→ REST APIで全テキストを収集 + スナップショット比較に切り替え。

📖 同じ用語を異なる意味で解釈

「前処理」がノードなのか学習の準備段階なのか曖昧で、見当違いの範囲を測定してしまいました。

→ 用語が曖昧なら測定前に範囲を確認するよう手順・メモリに反映。

🔗 文書のリンクをチップにできない

文書APIがタスクのメンションに対応していないことを、自分で試して確認しました。

→ 「番号+タイトル」のリンクに標準化し、画面で変えた書式が上書きで消えないよう追記を優先。

📐 ダイアグラムが画面で切れる

Obsidianの表示幅を超えたダイアグラムが切れて表示されました。

→ レンダリングして幅を測り、600px以下に再設計。

学び
